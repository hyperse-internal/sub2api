# 源码部署

按 [README](../../README.md)「Method 4: Build from Source」从本仓库编译并运行。前端打进 Go 二进制，运行时不再单独起 Node。PostgreSQL 与 Redis 需事先就绪，不随本流程安装。

线上机 `156.225.27.147` 当前走的是安装脚本布局（`/opt/sub2api` + systemd），不是 Docker。覆盖升级只替换 `/opt/sub2api/bin/server`，沿用现有 PostgreSQL 库 `sub2api` 和 Redis DB 1。不要重跑安装向导，不要覆盖 `config.yaml`、`.env`、`.installed`，不要清空数据库或 Redis。

## 依赖

| 组件 | 版本 |
| --- | --- |
| Go | 1.27.2（`backend/go.mod`） |
| Node.js | 18+ |
| pnpm | 前端包管理器 |
| PostgreSQL | 15+ |
| Redis | 7+ |

生产机已核对：PostgreSQL 16.15、Redis 7.0.15、Nginx、systemd 都在跑。Node.js 22 有，**没有 Go**，所以不要在这台机器上编译。在开发机交叉编译出 Linux amd64 二进制再拷上去。内存已用约 11G、剩余约 4G，不适合在生产机上编前端和后端。

## 编译

在有 Go 1.27.2 和 pnpm 的开发机上，于仓库根目录执行。目标机器是 linux/amd64：

```bash
cd frontend
pnpm install
pnpm run build
# 产物：backend/internal/web/dist/

cd ../backend
VERSION="$(./scripts/resolve-version.sh)"
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
  go build -tags embed -ldflags="-X main.Version=${VERSION}" -o server ./cmd/server
```

必须带 `-tags embed`。不带这个 tag 时，二进制不包含管理界面。`CGO_ENABLED=0` 得到静态二进制，和生产机上现有的 `/opt/sub2api/bin/server` 一样，不依赖本机 libc 以外的动态库。

开发热更新不走这条构建：后端 `cd backend && go run ./cmd/server`，前端 `cd frontend && pnpm run dev`。

## 覆盖升级当前生产

这是本次要走的流程。服务会有一次重启空窗（迁移完成前 Nginx 会暂时连不上 8080），数据库和 Redis 里的数据保留。

### 为什么不会重装

`config.yaml` 或 `.installed` 任一存在时，`NeedsSetup()` 为 false。生产上两者都在，因此即使 `.env` 里 `AUTO_SETUP=true`，新进程也不会重写配置、不会重建管理员、不会清库。启动后 `InitEnt` 调用 `ApplyMigrations`：按文件名跳过 `schema_migrations` 里已有的迁移，只执行未应用的 SQL。已应用文件的 checksum 对不上会启动失败。旧二进制只留在 `/opt/sub2api/backup/server.prev`，按下面的回滚换回去。

当前库已应用 292 个迁移，最新是 `242_drop_platform_check_constraints.sql`。本仓库还多 4 个，重启时会补上，都是加列或加表，不删现有业务数据：

- `242_group_i18n.sql`
- `243_gemini_cached_contents.sql`
- `244_gemini_cached_contents_channel_usage.sql`
- `245_gemini_cached_contents_mutation_lease.sql`

Redis 只做会话、限流和调度缓存。不要 `FLUSHDB`，也不要改 `config.yaml` 里的 `redis.db`（现为 `1`）。`jwt.secret` 和 TOTP 密钥必须保持不动，否则已登录会话和已绑定的二次验证会失效。

`docs/deploy/config/` 是对照用的副本，升级时不要把它覆盖到服务器上。

### 升级前备份

在服务器上：

```bash
install -d -m 700 /opt/sub2api/backup
cp -a /opt/sub2api/bin/server /opt/sub2api/backup/server.prev
cp -a /opt/sub2api/config.yaml /opt/sub2api/.env /opt/sub2api/.installed /opt/sub2api/backup/
sudo -u postgres pg_dump -Fc -d sub2api -f /opt/sub2api/backup/sub2api.dump
```

不要备份时重启或清空 Redis。Redis 数据留在 `127.0.0.1:6379` 的 1 号库里，随进程重启继续使用。

### 替换二进制并重启

在开发机上把 `backend/server` 传到服务器，例如 `/opt/sub2api/bin/server.new`。然后在服务器上：

```bash
chmod 755 /opt/sub2api/bin/server.new
mv /opt/sub2api/bin/server.new /opt/sub2api/bin/server
systemctl restart sub2api
systemctl status sub2api --no-pager
```

`mv` 到正在运行的路径后再 restart：旧进程在重启前仍占用旧 inode，不会在拷贝过程中跑到一半的文件。

看迁移是否跑完、进程是否起来：

```bash
journalctl -u sub2api -n 80 --no-pager
curl -fsS http://127.0.0.1:8080/health
curl -fsS -o /dev/null -w "%{http_code}\n" https://ai.alphaio.vip/health
```

本机 `8080` 返回成功，且公网 `/health` 为 200，即升级完成。再用原管理员账号登录 `https://ai.alphaio.vip`，确认用户、渠道和设置还在。

### 回滚

迁移失败时进程起不来，库停留在失败的那一个迁移之前（这 4 个文件在事务里执行）。把备份的二进制换回去：

```bash
systemctl stop sub2api
cp -a /opt/sub2api/backup/server.prev /opt/sub2api/bin/server
systemctl start sub2api
```

这 4 个迁移已经成功、但新版本行为不对时，旧二进制仍能读原有表；新表和新列会被旧版本忽略。只有确认需要把库也退回去时，才用 `/opt/sub2api/backup/sub2api.dump` 做 `pg_restore`。那会丢掉升级之后写入的数据，默认不要做。

不要为了回滚去删 `config.yaml` 或 `.installed`。删掉后下次启动会认为未安装：没有 `AUTO_SETUP` 时进入安装向导，有 `AUTO_SETUP=true` 时会再次从 `.env` 写配置。生产 `.env` 里这两项都在，误删锁文件有覆盖 `config.yaml` 的风险。

## 首次安装（不要用于当前生产）

下面只适用于空库。当前生产已经有 `config.yaml`、`.installed` 和业务数据，按上一节覆盖升级，不要执行这里的向导步骤。

管理员只由首次打开的安装向导创建。`config.yaml` 里的 `default.admin_email` / `default.admin_password` 不会建号。

启动前如果工作目录里已经有 `config.yaml`，向导会被跳过，用户表为空，登录会报 `invalid email or password`。

推荐做法：先不要复制配置模板，直接运行二进制。浏览器打开 `http://<host>:8080`，向导写入数据库、Redis 和管理员，并生成 `config.yaml`。

已经放好 `config.yaml` 时：

```bash
mv config.yaml config.yaml.bak
./sub2api
# 向导完成后停掉进程
mv config.yaml.bak config.yaml
./sub2api
```

## 安装到当前线上布局

当前服务单元（`/etc/systemd/system/sub2api.service`）约定：

| 项 | 路径 |
| --- | --- |
| 工作目录 | `/opt/sub2api` |
| 二进制 | `/opt/sub2api/bin/server` |
| 环境文件 | `/opt/sub2api/.env` |
| 进程配置 | `/opt/sub2api/config.yaml` |
| 日志 | `/opt/sub2api/logs/stdout.log`、`stderr.log` |

这台机器首次安装时 `AUTO_SETUP=true`，由 `.env` 生成了 `config.yaml`（2026-10-10）。之后监听、数据库、Redis、JWT 以服务器上已经生成的 `config.yaml` 为准。后台里的站点、支付、OAuth、返利等开关在 PostgreSQL 库 `sub2api` 的 `settings` 表，不在这两个文件里。覆盖升级时这些都保持不动。

对外入口是 Nginx：`/etc/nginx/sites-available/ai.alphaio.vip`，反代到 `127.0.0.1:8080`。站点里需要 `underscores_in_headers on;`，否则带下划线的头（例如 `session_id`）会被丢掉，多账号粘性会话会失效。

## 需要的配置文件

部署前要准备或确认的文件：

| 文件 | 作用 | 怎么来 |
| --- | --- | --- |
| `deploy/config.example.yaml` | 全量配置模板，不直接被进程读取 | 仓库自带 |
| 工作目录下的 `config.yaml` | 进程启动配置：监听、数据库、Redis、JWT、安全项 | 向导生成，或从模板复制后修改。线上路径 `/opt/sub2api/config.yaml`（权限 `600`） |
| `deploy/sub2api.service` | systemd 单元模板 | 仓库自带。线上已安装为 `/etc/systemd/system/sub2api.service`，并额外使用 `EnvironmentFile=/opt/sub2api/.env` |
| `/opt/sub2api/.env` | 首次自动安装用的环境变量（库、Redis、`SERVER_*`、`ADMIN_EMAIL`、`JWT_SECRET`、`TOTP_ENCRYPTION_KEY`） | 线上已有，权限 `600`。源码方式若走安装向导，不必再手写 |
| Nginx 站点配置 | HTTPS 反代、请求体大小、流式超时、`underscores_in_headers` | 线上为 `/etc/nginx/sites-available/ai.alphaio.vip` |

`config.yaml` 里启动时必须填对的块：

```yaml
server:
  host: "0.0.0.0"   # 仅本机反代时用 127.0.0.1
  port: 8080
  mode: "release"

database:
  host: "localhost"
  port: 5432
  user: "postgres"
  password: "your_password"
  dbname: "sub2api"

redis:
  host: "localhost"
  port: 6379
  password: ""

jwt:
  secret: "change-this-to-a-secure-random-string"   # openssl rand -hex 32
  expire_hour: 24
```

同一文件里还有这些可选块，默认值见模板：`cors`、`security`（含 `url_allowlist`、`trusted` 代理与客户端 IP 头）、`gateway.openai_ws`、`billing`、`turnstile`、`run_mode`。生产环境把 `security.url_allowlist.allow_insecure_http` 设为 `false`，避免上游地址走明文 HTTP。`jwt.secret` 和 TOTP 加密密钥更换后，已登录会话和已绑定的二次验证会失效。

不要和源码部署混用的文件：

| 文件 | 说明 |
| --- | --- |
| `deploy/.env.example` | Docker Compose / Apple container 的环境变量模板，复制为 `deploy/.env` |
| `deploy/docker-compose.yml`、`deploy/docker-compose.local.yml` | 容器部署，自带 PostgreSQL 与 Redis |

运行后由程序写出、一般不用手改的内容：`data/`（含 `model_pricing.json`）、`data/plugins`、`data/pages`，以及库表 `settings`。
